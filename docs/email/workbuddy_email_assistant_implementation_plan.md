# WorkBuddy 邮件数字助理实施方案

## ImapFlow + MailParser + 只读 MCP + 每日摘要与紧急提醒

**文档版本：** v1.0  
**编制日期：** 2026-10-08  
**适用场景：** 为大型药企临床前总监建设私人 AI 助理，接入其获授权的国内企业邮箱，并通过企业微信提供每日简报与紧急邮件提醒。  
**文档用途：** 产品范围确认、开发任务拆解、IT/信息安全评审及交付验收。

> 本文件是待实施的工程设计，不代表已经连接客户邮箱或完成 WorkBuddy 联调。邮箱厂商、客户端访问政策、模型端点、企业微信发送权限尚未确认。文中的频率、容量和指标均为建议初值或验收目标，不是软件默认值、客户既定要求或生产服务承诺。任何真实邮件接入及自动推送，都应在相应授权完成后开启。

## 0. 方案结论与阅读导航

**采用一个常驻邮件服务，而不是让一条 WorkBuddy 会话持续盯着邮箱。**

邮件服务负责可靠同步、解析、分析、调度和通知；WorkBuddy 通过只读 MCP 查询邮件及分析结果，提供追问、解释和人工查阅。每日摘要和紧急提醒即使在总监没有打开 WorkBuddy 时，也应能由后台独立运行。

| 组成 | 本方案中的职责 |
| --- | --- |
| ImapFlow | 使用获批准的 IMAP 连接读取邮件；不连接 SMTP |
| MailParser | 解析 MIME 邮件、正文、地址与附件元数据 |
| 业务后台 | 增量同步、线程关联、规则判断、模型调用、任务持久化、定时汇总 |
| PostgreSQL | 保存同步状态、邮件缓存、分析结果、待办、简报和通知记录 |
| 只读 MCP | 为 WorkBuddy 提供受身份与数据范围约束的查询能力 |
| 三个定制 Skill | 邮件研判、每日简报、紧急提醒解释；与后台共享分析规范 |
| 企业微信通知适配器 | 向已绑定且获授权的本人发送通知，不向模型开放任意发送权限 |
| Obsidian | 后续按需保存经确认的项目摘要；首期不自动复制整个邮箱 |

**建议先阅读：** 第 1—4 节确认范围与架构；第 5—13 节用于开发；第 14—17 节用于上线与验收；第 18 节可直接作为开发交接说明。

**第一版的四条红线：** 不改邮箱、不代发邮件、不把邮件原文发送到未经批准的服务、不把监控失败解释为“没有重要邮件”。

## 1. 目标、范围与交付边界

### 1.1 需要实现的业务能力

1. **每日工作简报。** 按项目和事项组织邮件，呈现本人待处理事项、项目变化、等待对方事项及其他知会信息；每条重要结论能定位到邮件证据。
2. **紧急邮件主动提醒。** 新邮件到达后，结合已确认规则、截止时间和必要的线程上下文判断是否需要提醒本人；支持去重、重试、免打扰与失效告警。
3. **通过 WorkBuddy 查询与追问。** 例如“为什么这封被标成紧急”“这个 CRO 最近还有哪些未决问题”“展开今天简报的第二项”。
4. **可追溯与可维护。** 能看到最后同步时间、解析失败、待分析积压、推送结果、采用的规则与模型版本。

### 1.2 首期范围

| 事项 | 第一版安排 |
| --- | --- |
| 试点用户 | 一位总监、一个获授权邮箱；数据结构预留账号隔离 |
| 文件夹 | INBOX，以及确认会被收信规则自动分流的文件夹 |
| 已发送邮件 | 获授权后读取，用于辅助判断回复情况；没有接入时明确显示覆盖限制 |
| 邮件正文 | 中文、英文、混合语言；纯文本和 HTML 邮件 |
| 附件 | 先读取文件名、类型、大小和是否存在；内容解析为后续受控扩展 |
| 每日摘要 | 按明确配置的业务时区和时间运行；首期只设置一个每日推送计划 |
| 即时提醒 | 按本人确认的规则，仅推送到获授权的本人通知渠道 |
| 写操作 | 后台可写入自己的数据库；不得修改源邮箱 |
| 通知确认 | 通过独立、需登录的确认页面处理；不混入只读 MCP |

### 1.3 明确不做

不自动回复、转发、删除、归档、标记已读或移动邮件；不修改邮箱规则；不自动点击链接、下载外链或接受会议邀请；不把项目邮件用于模型训练；不自动把私人邮件开放给团队分身；不根据邮件内容批准研究方案、项目启动或正式报告。

**“只读”指源邮箱和面向 Agent 的业务工具只读，不代表整个后台不能写自己的处理记录。** 通知投递属于另一个受控服务动作，不是“发送邮件”。

### 1.4 第一版不引入的复杂组件

不默认引入 Redis、Kafka、向量数据库、多专家 Agent、整套工作流平台或 Kubernetes。先以一个代码仓库、一个 PostgreSQL 和可独立运行的 Worker/API 完成闭环。确实遇到吞吐量、检索或组织级隔离需求后再扩展。

## 2. 上线前需要客户确认的事项

下表由实施方与 IT 集中核对，不需要总监自行研究协议参数。

| 确认项 | 需要取得的信息 | 未确认时如何处理 |
| --- | --- | --- |
| 邮箱服务 | 厂商、产品版本、公有云/专有云/自建、服务器地址 | 不猜服务器，不接真实账户 |
| 协议与认证 | 是否允许 IMAP，密码/专用授权码/OAuth，是否需客户端审批 | 只做模拟邮箱开发 |
| 网络 | 部署位置、固定出口、端口、IP 白名单、代理、企业 CA | 不通过关闭 TLS 校验绕过 |
| 数据范围 | 可读取的账户、文件夹、历史范围、敏感内容限制 | 默认不开全邮箱扫描 |
| 模型 | 获准端点、数据区域、日志与保留政策、是否允许正文发送 | 不向外部模型发送邮件 |
| 企微通知 | 是否可建应用、可见范围、本人身份映射、推送权限 | 仅生成本地待发送记录 |
| 日程偏好 | 业务时区、每日推送时间、周末安排、夜间提醒规则 | 调度和真实推送保持关闭 |
| 紧急规则 | 必须提醒的事项、重要项目、联系人、截止时间处理 | 使用标注样本验证，不直接自动上线 |
| 保留与删除 | 邮件缓存、摘要、日志、备份及撤销授权后的删除策略 | 未批准前不持久化真实正文 |
| 维护责任 | 邮箱管理员、业务规则负责人、故障接收人 | 不进入无人值守运行 |

**建议业务时区：** 此场景可先提出 `Asia/Shanghai` 供客户确认，但不以实施者电脑时区或服务器时区代替总监的业务时区。涉及海外 CRO 的截止时间，另保留原文时区。

**协议不可用时的决策：** 优先评估厂商正式 API 或企业授权的替代通道；未经批准，不改为网页抓取或自动转发整个邮箱。

## 3. 技术选型与版本策略

### 3.1 建议技术栈

| 层级 | 建议选择 | 说明 |
| --- | --- | --- |
| 运行时 | 企业批准、仍受支持的 Node.js LTS + TypeScript | 在启动阶段确认并锁定版本，不在方案中猜测客户环境 |
| IMAP | `imapflow` | 官方提供 UID 获取、只读打开文件夹及 IDLE 等能力 [1] |
| MIME 解析 | `mailparser` | 小邮件可用 `simpleParser`；较大内容采用流式 `MailParser` [3] |
| 数据库 | PostgreSQL | 统一存状态、任务和业务结果；使用事务保证任务与状态一致 |
| MCP | 官方 TypeScript SDK | 新项目评估 SDK v2，并验证 WorkBuddy 的协议与工具调用兼容性 [7] |
| 参数校验 | 与所选 SDK 兼容的 Schema 库 | 外部输入、模型输出和工具结果均校验 |
| HTTP 服务 | 一个受支持的 Node.js Web 框架 | 选一种即可，承载管理接口和远程 MCP |
| 定时与任务 | PostgreSQL 持久任务表 + Worker + 单一调度入口 | 不依赖仅存在内存里的定时器状态 |
| 模型调用 | 企业批准的独立 API 客户端 | 不假设 WorkBuddy 桌面订阅包含后台模型调用能力 |
| 部署 | 企业已有服务管理方式，或受控容器部署 | API、Worker、通知进程逻辑隔离 |

### 3.2 版本约束

当前官方 MCP TypeScript 文档提供 v2 路线，包结构与旧版 `@modelcontextprotocol/sdk` 不同。新项目可按 `@modelcontextprotocol/server` 及相应传输/框架适配包构建；**不能把 v1 的导入路径直接混到 v2 工程里。** 最终选型以目标 WorkBuddy 的握手、认证和工具调用联调结果为准。[7]

所有依赖写入锁文件；生产镜像固定版本。升级 ImapFlow、MailParser、MCP SDK、模型或提示词时，都要运行回归测试。禁止生产环境启动时自动安装未锁定的 `latest`。

### 3.3 已核对的几个实现注意点

ImapFlow 支持 `getMailboxLock(path, { readOnly: true })`。其文档特别提醒：不要在 `fetch()` 的异步迭代循环里再执行其他 IMAP 命令，否则会发生死锁。[1][2]

MailParser 的 `simpleParser` 会把附件等内容一起缓存在内存中；生产系统不能用它无限制地解析任意大小的邮件。MailParser 也不会自动完成 HTML 安全清洗。[3]

WorkBuddy 支持自定义 MCP 和 Skill；远程连接器支持相应传输与认证配置。具体配置字段应与客户实际安装版本核对。[5][6]

## 4. 系统架构与责任分工

### 4.1 总体数据流

```text
企业邮箱（IMAP；只读访问）
             |
             v
mail-sync-worker（发现新增 UID、登记任务、读取正文）
             |
             v
解析与标准化（MailParser、正文段落、线程候选）
             |
             v
PostgreSQL（源数据引用、工作队列、状态、业务结果）
             |
             +--> analysis-worker
             |       规则筛选 -> 获准模型 -> Schema/证据校验
             |                             |
             |                             v
             |                       通知决策与 Outbox
             |
             +--> daily-digest-job
             |       固定快照 -> 事项汇总 -> 简报校验 -> Outbox
             |
             +--> 只读 MCP API <--> WorkBuddy 私人邮件专家
             |
             +--> 私人确认页面（身份验证；独立写接口）

Outbox -> notification-worker -> 企业微信本人通知渠道
                                   |
                                   v
                         查看详情 / 明确确认 / 查看状态

独立运行监控 -> IT 故障渠道（不包含敏感邮件正文）
```

### 4.2 后台与 WorkBuddy 不重复做调度

**生产推荐：每日摘要和新邮件分析均由后台负责。** WorkBuddy 安装的 Skill 读取已有结果，并解释、展开或在当前对话中形成临时摘要。

后台不是“远程执行 WorkBuddy 的 Skill 文件”。后台直接调用获批准的模型 API，读取与 Skill 共享的版本化分析规范。两者复用的是规则、字段和输出模板，而不是未经确认的桌面调用接口。

因此，关闭 WorkBuddy、结束对话或清空某次会话，不应影响邮箱监控。相反，后台停机时，WorkBuddy 应报告数据可能不新鲜，而不是回答“没有新邮件”。

**避免双调度：** 不再同时给 WorkBuddy 配置一个同样的自动晨报任务。后续若改由 WorkBuddy 调度，应明确迁移主调度权并停用旧任务。

### 4.3 进程隔离

| 进程 | 可取得的秘密 | 不应取得的秘密或权限 |
| --- | --- | --- |
| 同步 Worker | 获授权邮箱凭证 | 企业微信发送凭证、无关系统凭证 |
| 分析 Worker | 批准的模型凭证；限定的数据读取权 | 邮箱登录凭证、通知渠道密钥 |
| MCP API | 当前调用者身份；只读业务查询权 | 邮箱登录凭证、任意通知发送权 |
| 通知 Worker | 固定通知通道的凭证 | 邮箱凭证、任意原始附件读取权 |
| 管理/确认页面 | 受认证的本人或管理员身份 | 不允许仅凭链接参数冒充本人 |

单人试点可以共用一个主机，但仍应分离配置与权限。生产是否需要更强隔离，由企业安全要求决定。

## 5. 数据模型与状态机

### 5.1 核心表

下列是逻辑表设计，可合并部分辅助字段，但不要省掉同步、通知和证据状态。

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `mail_accounts` | id、owner_id、provider、secret_ref、timezone、policy_version、enabled | 账户配置；只存密钥引用 |
| `mail_folders` | account_id、path、uid_validity、discovered_uid、last_checked_at、sync_status | 每个文件夹独立同步状态 |
| `mail_deliveries` | id、folder_id、uid_validity、uid、internal_date、discovered_at、message_id、fetch_status | 邮箱中的具体投递实例 |
| `mail_messages` | id、account_id、thread_id、rfc_message_id、from/to/cc、subject、sent_at、body_text、parse_status、body_version | 可供分析的消息内容 |
| `mail_threads` | id、account_id、link_method、link_confidence、last_message_at | 往来关系；弱关联不能冒充确定线程 |
| `mail_analysis` | message_id、input_hash、policy/model/prompt_version、result_json、status | 可复用、可审计的结构化分析 |
| `action_items` | owner_id、thread_id、source_message_id、action_text、deadline、status、evidence_refs | 待处理事项与来源 |
| `job_queue` | kind、dedup_key、status、attempts、run_after、lease_until、payload_ref | 持久化任务与重试 |
| `daily_briefs` | owner_id、local_date、timezone、coverage_manifest、content、status、supersedes_id | 冻结的每日简报及覆盖范围 |
| `notification_outbox` | owner_id、event_key、channel、payload、status、provider_id、attempts | 可靠通知投递 |
| `user_feedback` | actor_id、target_id、feedback_type、reason、created_at | 确认/误报/漏报反馈，不直接改正式规则 |
| `audit_events` | actor/service、operation、resource_id、policy_version、result、timestamp | 审计；默认不记正文和密钥 |

### 5.2 两层身份，不能混为一谈

**投递实例的唯一约束：**

```text
UNIQUE(folder_id, uid_validity, uid)
```

`folder_id` 已绑定账号。IMAP 的 UID 需要结合文件夹和 UIDVALIDITY 理解，不能用序号或 UID 单独作为全局主键。UIDVALIDITY 改变后，原 UID 映射必须失效并重新核对。[4]

**跨文件夹重复消息：** 使用 `Message-ID` 与经核对的内容特征判断候选重复；缺失、重复或伪造的 `Message-ID` 不得导致错误合并。正文不同的消息即便 Message-ID 相同，也必须保留为独立消息并标记异常。原始投递实例始终保留。数据库与接口统一规定 UIDVALIDITY 的类型；若库返回 JavaScript BigInt，序列化 JSON 前转为十进制字符串，不直接 JSON.stringify(BigInt)。

### 5.3 必须分开的状态

```text
同步：discovered -> queued -> fetched | unavailable | failed
解析：pending -> parsed | partial | failed | blocked_by_policy
分析：pending -> valid | needs_review | failed
通知：pending -> sending -> accepted | retry_wait | unknown | permanently_failed
事项：candidate -> open -> waiting_other -> resolved_candidate -> confirmed_closed
```

`accepted` 只表示通知平台接受请求，不代表总监已读。`confirmed_closed` 需要明确的人类确认或事先批准的确定性业务规则；不能只看到对方回复“收到”就自动关闭。

`unknown` 表示网络超时等情况下无法确认平台是否收到，不能当作“未发送”无限快速重试。

### 5.4 证据定位

正文标准化后按段落生成稳定 ID，例如 `p0001`、`p0002`；保存 `body_version`。模型只能引用本次输入里存在的消息 ID、段落 ID 与摘录。

```json
{
  "message_id": "msg_demo_001",
  "body_version": "body-v1",
  "paragraph_id": "p0003",
  "quote": "请于北京时间明日中午前确认是否接受新的交付安排。"
}
```

这是结构示例，不是真实邮件。后台校验段落存在、摘录匹配，并检查结论是否有对应依据；摘录能匹配并不自动证明模型的解释正确。

## 6. 邮件同步实施

### 6.1 初次连接与基线

1. 经授权后测试 TLS、认证和文件夹列表；确认 INBOX 及自动分流文件夹的真实路径，不猜中文文件夹名称。
2. 建立只读会话，读取各文件夹 UIDVALIDITY 和 UIDNEXT，记录本次启用基线。
3. **实时新增通道先启用，历史回填另排低优先级任务。** 初次基线的 `H0 = UIDNEXT - 1` 作为实时通道起点；更早邮件由独立回填游标处理，回填不能倒退或覆盖实时游标。不应为了扫描历史邮件而延迟处理刚收到的重要邮件。
4. 历史回填范围由客户批准，例如最近 7 天。历史邮件标记为 `backfill`，不直接触发新邮件紧急提醒。
5. 回填发现仍可能未解决的重要旧事项时，放入一次性的“待确认历史事项”，避免把几个月前的紧急邮件重新轰炸总监。

### 6.2 增量同步算法

采用“发现任务”和“获取/分析”分离的方式。以下为算法说明，不是可直接运行的完整代码。

```text
sync_folder(folder):
  获取该文件夹的服务端任务租约，串行使用 IMAP 连接
  以只读方式打开文件夹
  读取 UIDVALIDITY 与 UIDNEXT

  如果 UIDVALIDITY 与保存值不同:
    将旧映射标记为待重建
    建立新的同步代次与受控重建任务
    暂停使用旧游标，显示覆盖状态不完整
    对重建消息复核重复关系，避免重新发送全部旧提醒
    返回

  L = discovered_uid + 1
  H = UIDNEXT - 1
  如果 L > H:
    记录本次成功检查时间
    返回

  在明确的闭合范围 L..H 内分页查找实际存在的 UID
  对每批发现的 UID，在一个数据库事务中:
    幂等写入 mail_deliveries
    幂等登记 fetch/parse 任务
    保存这一批已经完整登记的范围进度

  仅在整个范围扫描成功且任务已持久化后:
    将 discovered_uid 推进至 H
    保存 last_checked_at

  获取与解析失败由独立任务重试，不重新推进发现游标
```

**关键约束：**

- 不用消息序号做持久化游标；序号会随删除等操作变化。[4]
- 不以 `UNSEEN` 或邮件标题时间为增量依据；已读邮件同样需要进入分析范围。
- 不直接使用不加边界保护的 `last_uid + 1:*`；空范围时不应错误拉取尾部消息。
- UID 不要求连续；推进的是已完整扫描的 UID 范围，不是假定每个数字都存在。
- 必须先把发现记录及任务落库，再提交游标。不能先跳过 UID，随后才尝试建任务。
- 把“发现到了 H”与“全部解析到了 H”分开统计；发现成功不代表分析没有积压。
- 邮件在被读取前已被源邮箱移走或删除时，记录 `unavailable` 并核对授权文件夹，不能承诺恢复不存在的数据。

### 6.3 新邮件触发与定时核对

ImapFlow 的 IDLE/事件用于提示当前打开文件夹的变化；它不是整个账号全部文件夹的永久订阅。[1]

建议初始运行策略：INBOX 保持监听，并每 2 分钟执行一次增量核对；其他已授权收信文件夹同样按配置核对。轮询值是建议初值，须按邮箱连接限制及压测结果调整。

单账号第一版可用一个串行连接：切换到其他文件夹核对后，回到 INBOX 监听。若邮箱限制允许且实测需要，可分为监听连接和同步连接，但不能无限增加连接数。

收到 `exists` 等事件时，仅合并登记同步任务；不要在事件回调里并发读取“最后一封邮件”。即使邮件总数未变，也可能发生“一封新增、一封移走”，因此必须保留定期核对。

### 6.4 断线、重启与限流

由后台显式实现重连状态机：监听错误及关闭事件，释放资源，退避重连，重新读取 UIDVALIDITY，再从持久状态补拉。不能把库的 IDLE 能力当成完整的断线恢复服务。

建议重试从短间隔开始，逐步增长并加入随机抖动；认证失败应进入待人工处理，避免反复尝试导致账户被锁定。网络故障、协议错误、凭证失效分别分类。

任务使用租约；Worker 中断后，租约过期的任务可重新领取。重复执行必须依靠唯一键和事务保持幂等。

### 6.5 只读访问验收

同步代码只暴露必要的列表、状态、搜索和读取方法；不得向业务模块传递能执行任意 IMAP 操作的客户端对象。使用只读文件夹打开方式，确保正文读取不修改标志，并通过独立邮箱客户端验证已读状态、文件夹位置和标志没有变化。[1][4]

**重要限制：** 应用的 `readOnly` 模式不一定意味着邮箱授权码本身只有读权限。若邮箱不能提供真正的只读授权，需要通过专用进程、网络和代码审计降低风险，并在安全评审中记录剩余风险。

## 7. 解析、线程与内容安全

### 7.1 两级读取

**第一层：轻量读取。** 获取 UID、内部投递时间、邮件头、大小和 MIME 结构，识别是否需要大文件处理。

**第二层：受控正文读取。** 对小邮件读取完整 MIME 并由 MailParser 解析；对大邮件优先获取正文部分和附件元数据，或使用流式解析。不要为了识别一封带大附件的短邮件，先把全部附件放入内存。

建议 `simpleParser` 的原始邮件上限先设为 5 MiB，标准化文本输入上限另设。这些只是保护性初值。超过阈值不等于丢弃邮件，而是进入分段/流式路径并记录是否完整。

### 7.2 标准化处理

保留发件人、收件人、抄送、Reply-To、Message-ID、References、In-Reply-To、原始发送时间和 IMAP 内部时间。MailParser 提供相应的题录与正文解析字段。[3]

优先使用纯文本；仅有 HTML 时转换为不执行脚本、不加载网络资源的文本。保留经授权的原文对照以及引用段落位置；剥离签名和历史引用仅用于降低分析冗余，不能破坏证据来源。

**不要做：** 加载远程图片、自动访问邮件链接、执行宏或脚本、展开压缩包、自动调用公开检索补全邮件中的内部信息。

### 7.3 线程关联

优先使用 `References` 和 `In-Reply-To` 关联，再考虑厂商提供的可靠线程标识。仅凭相同主题、`Re:` 或相同联系人建立的关系标记为候选，不当作确认事实。

回复中引用旧的“紧急”语句，不一定构成新的紧急事件。分析时区分本次新增正文、引用历史和其他独立邮件。

已发送文件夹未授权、未同步或覆盖不完整时，显示：**“未在当前可见邮件范围内发现回复，不能确认本人尚未回复。”** 已读标志也不能作为事项已完成证据。已发送文件夹主要用于状态补充，不把本人普通发信作为“新收到的紧急邮件”重复通知。

### 7.4 附件边界

首期通知可以写“邮件含研究报告附件，附件内容尚未分析”，不能说“已审阅报告”。正文写“紧急问题见附件”但附件未读时，应进入人工核查，而不是判为无风险。

后续接入附件解析时，新增文件类型白名单、恶意文件检测、单文件/解压限额、隔离执行和无外网沙箱。扫描 PDF、加密文件或无法可靠提取的表格应明确显示覆盖不足。

### 7.5 邮件注入与伪造风险

邮件内容、附件文字和模型总结均按不可信内容处理。诸如“忽略规则”“修改提醒联系人”“把附件发到此处”的语句都只是邮件数据，不是系统指令。

重要联系人匹配不能只看显示名称；至少核对完整邮箱地址与企业维护的联系人表。域名/地址匹配也不等于真实性已确认。仅可使用可信邮件系统给出的验证结果；不能信任转发正文里伪造的 Authentication-Results。

业务紧急与安全可疑是两个独立维度。一封疑似冒充高管的邮件可能值得提醒，但提醒应是“身份待核实”，不是建议按邮件要求付款、共享资料或点击链接。

## 8. 摘要与紧急程度判断

### 8.1 三层决策

```text
确定性规则与数据完整性检查
              ↓
受限模型：提取事实、待办、期限、变化与证据
              ↓
后台策略：校验证据、计算时间、决定推送或待核查
```

模型不决定通知对象、不创建发送地址、不修改规则，也不直接调用通知服务。没有依据的紧急判断不能自动变成确定事件；已命中的本人确认的强制提醒规则不能被模型随意降级。

### 8.2 建议优先级

| 级别 | 定义 | 处理方式 |
| --- | --- | --- |
| P0：立即关注 | 命中已确认的必须提醒规则，或等待下一处理窗口可能产生实质影响且需本人介入 | 推送本人；夜间策略另行授权 |
| P1：本工作时段处理 | 明确待办、审阅或回复，但尚不需立即打断 | 工作时段待办/每日简报；临近窗口时重新评估 |
| P2：一般知会 | 普通进度、参考、订阅或无需本人动作 | 纳入简报或归入次要信息 |
| needs_review：待核查 | 内容、时间、身份或附件覆盖不足 | 根据潜在影响决定是否发“待核查”提醒；不假装已完成判断 |

`needs_review` 是分析状态，不必作为 P0/P1/P2 的互斥替代。例如，可以是“潜在 P0，附件未读，需要本人查看”。

### 8.3 临床前总监的初始业务规则候选

以下规则应由总监确认，不是行业统一标准：关键 CRO 交付突变且可能影响已确认里程碑；本人必须限时作出的决定；项目相关质量问题升级；当天关键会议取消或大幅改期；客户内部明确列为必须提醒的发件人/事项组合。

不能只因为出现“urgent”“ASAP”“紧急”就 P0，也不能把所有 CRO 发件人一律标为高优先级。没有项目台账支持时，使用“可能影响，尚需核对”，不能编造具体业务后果。

### 8.4 输出契约示例

以下结构用于开发 JSON Schema；样例内容均为虚构。

```json
{
  "message_id": "msg_demo_001",
  "analysis_status": "valid",
  "priority_candidate": "P1",
  "project_id": null,
  "topic": "交付日期确认",
  "summary": "发件人请求确认是否接受新的交付日期。",
  "action_required": true,
  "action_owner": "mailbox_owner",
  "suggested_action": "核查项目安排后，决定是否接受调整。",
  "deadline": {
    "raw_text": "明日中午前",
    "normalized_at": null,
    "source_timezone": null,
    "status": "needs_clarification",
    "evidence_ref": "msg_demo_001:p0003"
  },
  "urgency_reason": "存在限时确认要求，但原文时间基准尚未确定。",
  "evidence": [
    {
      "message_id": "msg_demo_001",
      "paragraph_id": "p0003",
      "quote": "请于明日中午前确认是否接受新的交付安排。"
    }
  ],
  "coverage": {
    "body_complete": true,
    "attachments_analyzed": false,
    "thread_complete": false,
    "sent_folder_available": false
  },
  "security_flags": [],
  "missing_information": ["截止时间适用时区", "是否已有后续回复"]

```

字段说明：`project_id` 只能从授权项目表选择，无法关联时为 null；`priority_candidate` 是模型建议，最终优先级由后台策略产生；缺失时间不要补成看似精确的时间点。

### 8.5 时间处理

同时保存发件人原文、邮件发送时间、IMAP 内部时间、收到/发现时间和业务时区。将“明天”解释为哪一天，应依据邮件原始上下文，而不是模型运行日期。

`EOD`、`下班前`、仅写日期等不明确表达，不默认等于北京时间 17:00。证据足够时由程序归一化；不够时保留原文和不确定状态。跨夏令时地区使用命名时区，不仅保存固定偏移。

### 8.6 输出校验与降级

后台至少检查：Schema 合法；ID 均在授权输入范围；证据真实存在；日期未被无依据补全；不是引用旧文造成的误判；没有“已批准/已回复/已完成”等无依据断言。

解析失败、模型超时或输出不合法时，可做有限次重试。仍失败则生成规则级最小结果，并列为待核查。强制提醒候选不得因模型不可用而静默丢弃。

采用低随机性配置、限定输入大小和超时；不把模型自报的“置信度 0.95”当成已校准概率。通过历史标注集评估真实误报和漏报。

### 8.7 通知去重

去重键建议由账号、稳定的业务事件身份、事件类型和证据版本组成。相同邮件重复抓取或模型重跑，不产生新的通知。

同一线程不能永久只提醒一次：新的截止时间、升级要求、关键附件补充或新的本人动作可构成新事件。另一个相反错误是只因多收到一句“谢谢”就重发原提醒。

若已出现后续解决证据，发送前应重新检查提醒是否仍适用。对必须升级的事项，不因模型猜测“可能解决”就自动撤销。

## 9. 每日摘要工作流

### 9.1 调度与输入快照

每日时间由本人明确确认，例如 `08:30 / Asia/Shanghai` 仅为配置示例。调度器将任务写入持久队列，并使用 `(owner_id, local_date, timezone, schedule_id)` 防止重复建任务。

生成前核对各授权文件夹同步新鲜度与分析积压。在数据库一致性快照中确定本期消息、待办、后续更新及未完成条目，并保存 `coverage_manifest`。

**不要只筛“过去 24 小时发出的邮件”。** 输入应包括上次已覆盖之后新发现/新处理的内容、迟到邮件、旧事项的新回复和仍未关闭的待办。发件人可填写错误日期，因此原始 Date 头不能独自决定遗漏与否。

### 9.2 四段式输出

```text
邮件工作简报
业务日期：YYYY-MM-DD；时区：Asia/Shanghai
数据截至：HH:mm；覆盖：INBOX + 已批准文件夹
状态：完整 / 部分内容待分析 / 同步异常

一、今天需要您处理
- 事项、最迟时间或“未明确”、建议下一步、证据

二、项目进展与变化
- 只列本期新增变化，不重复堆放历史邮件

三、等待对方或待确认
- 等待什么、对方是谁、上次明确动作、当前可见证据

四、其他知会与覆盖限制
- 次要信息压缩呈现
- 解析失败、未读附件、未接已发送文件夹等限制
```

推送渠道只发送获准的简短版本；完整简报通过受保护页面或 WorkBuddy 读取。关键事项不因文本长度限制被静默截掉，超限时按受控分页或链接处理。

### 9.3 持久化与发送顺序

```text
建任务 -> 确定快照 -> 生成/校验 -> 保存不可变简报版本
       -> 同事务登记 Outbox -> 通知 Worker 投递
       -> 平台接受后登记已覆盖状态
```

通知失败时重发同一简报版本，不重新生成另一份内容并重复计算窗口。手工重生成的新版本记录 `supersedes_id`，默认不自动再次推送，除非明确修正了关键错误并按批准策略发送更正。

简报中的事实、条数和截止时间由结构化数据核对。只有实际纳入简报的消息/事项版本才能登记为已覆盖；未解析、待分析或被截断未呈现的记录保持待处理，不因更新一个全局时间戳而被跳过。没有新的高优先级邮件与没有读取成功，是完全不同的状态。

### 9.4 断档与迟到内容

发生停机或积压时，后续简报须说明未覆盖时段，并补入迟到内容。已被确认关闭的事项，不因历史邮件回填而重新变成“待处理”。

只有当授权范围内同步和分析都符合完整性条件时，才允许输出“本期未发现需要立即关注的邮件”。否则应写“当前数据不完整，无法确认是否存在遗漏”。

## 10. 企业微信主动推送

### 10.1 首选方案与联调前提

**拟采用企业微信自建应用，定向通知总监本人。** 首期不依赖客户正在对话，不默认复用 WorkBuddy 智能机器人的会话回复通道。

上线前由 IT 验证自建应用权限、可见范围、实际 UserID、服务端发送方式、出口限制和平台限流。企业微信“发送应用消息”官方文档列于参考资料 [10]；本次未能完整读取该页面，因此本方案不把具体请求字段、频率或账号可用性当成已完成验证的事实。

WorkBuddy 官方 MCP 示例也演示了企业微信群 Webhook。[6] 但群通知不等于本人私信。除非群成员、内容范围和管理策略均已批准，否则不能把总监私人邮件推到群里。首期不把群 Webhook 作为默认降级通道。

### 10.2 通知适配器契约

这是本项目自定义接口，不是企业微信原生 API：

```ts
interface NotificationAdapter {
  send(input: {
    notificationId: string;
    ownerId: string;
    template: "urgent" | "daily" | "monitoring_degraded";
    approvedPayload: Record<string, unknown>;
  }): Promise<{
    status: "accepted" | "rejected" | "unknown";
    providerMessageId?: string;
    errorCode?: string;
  }>;
}
```

`ownerId` 在后台映射到固定收件人；模型不能传入任意 UserID、群 ID、URL 或 Webhook。正文由固定模板渲染并限制长度，标题和项目名同样按敏感信息处理。

### 10.3 通知内容

```text
[需关注] 存在一项限时确认请求
原因：邮件要求本人确认交付安排。
需要您处理：查看原邮件后决定是否接受。
时间：原文为“明日中午前”，适用时区待核查。
依据：消息编号 M-000123，第 3 段。
状态：附件内容尚未分析。
查看详情：已认证的私人详情页
```

上例为最小披露模板。能否包含 CRO 名称、项目号和具体研究事项，由客户通知策略决定。不得在锁屏可能显示的通知中默认展示完整研究内容。

### 10.4 投递可靠性

使用 Outbox 持久队列、唯一事件键和租约；只将平台明确接受的请求标为 `accepted`。对超时等不确定结果记录 `unknown`，结合平台可用的去重/查询机制做有界重试。

**不宣称跨系统“恰好一次”送达。** 若平台没有相应保障，网络故障后仍可能重复；在通知中保留稳定编号，并把此边界纳入验收。

发送前复核用户映射和提醒有效性。永久失败进入故障列表并通知已批准的 IT 渠道；不要自动改发其他人。

### 10.5 免打扰、确认与升级

夜间是否允许 P0 打扰，需要明确授权。未授权前不开夜间真实推送；白天/夜间策略及节假日必须配置化。

用户“确认已看到”和“事项已经处理”分成两个动作。确认页面应登录校验，采用明确的 POST 操作，不能由打开链接的 GET 请求直接完成，以免被预览机器人或安全扫描器误触发。

是否重复提醒、何时升级、升级给谁，由本人和企业规则决定。没有授权时，不向助理、上级或项目群升级。AI 邮件提醒不替代企业既有重大事项升级渠道。

| --- | --- | --- |
| `mail_get_sync_status` | 无账号切换参数 | 授权范围、最后检查时间、积压、失败及新鲜度 |
| `mail_search_messages` | query、from/to 时间范围、project_id、cursor、limit | 限定范围的邮件摘要及引用 |
| `mail_get_message` | message_id、paragraph_cursor、limit | 分页正文、题录、覆盖信息、证据段落 |
| `mail_get_thread` | thread_id、cursor、limit | 按时间排列的往来及关联可靠性 |
| `mail_get_daily_brief` | local_date | 已生成的简报版本与覆盖状态；不存在时明确返回 |
| `mail_get_pending_items` | project_id、status、cursor、limit | 待办及来源，不保证等于全部线下事项 |
| `mail_get_alert` | notification_id | 提醒理由、规则版本、证据、平台接受与本人确认状态 |

首期不提供 `send`、`delete`、`move`、`mark_read`、`update_rules`、任意 SQL、任意 HTTP 抓取、文件路径读取或 shell 执行工具。

### 11.2 服务端权限

调用者身份来自验证通过的连接器令牌/企业认证，不从模型传入的 `user_id` 或 `account_id` 决定权限。第一版每个令牌绑定一个本人账号；所有查询都在服务端附加 owner/account 范围。

仅给 MCP 业务查询使用只读数据库角色；审计写入使用隔离的记录通道。设置字段白名单、分页、时间跨度、返回字符数和调用频率上限。跨账号 ID 返回不可访问结果，不泄露另一个账号是否存在。

MCP 的工具元数据可以声明只读意图，但注解不是权限系统。输入校验和访问控制必须由服务实现。[8]

### 11.3 MCP 连接方式

生产优先使用 HTTPS 的远程 MCP，服务部署在企业批准的位置；WorkBuddy 需要从实际运行网络访问该服务。没有可批准的入站网络时，可用本地 stdio 代理连接后台受控 API；stdio 代理不是邮件常驻 Worker，关闭 WorkBuddy 只应关闭代理。

WorkBuddy 官方连接器文档支持 `streamableHttp`、`stdio` 等类型，并说明了凭证变量、Token/OAuth 路线。[5]

**示意配置，域名与令牌变量需通过客户版本的正式配置方式填入：**

```json
{
  "mcpServers": {
    "director-mail-readonly": {
      "type": "streamableHttp",
      "url": "https://mail-assistant.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${MAIL_MCP_ACCESS_TOKEN}"
      }
    }
  }
}
```

`example.com` 是示例域名，不是现成服务。环境变量替换或 Token 表单注入必须在目标 WorkBuddy 版本验证；不要将真实凭证直接写进聊天、Skill、仓库或导出的配置包。这里的 Token 是本项目服务令牌，不是邮箱密码。

优先复用企业身份认证与短期令牌；采用固定服务令牌试点时，绑定本人、缩小范围、设定过期和撤销机制。远程服务校验访问令牌及适用资源，不能仅因请求来自内网就免认证。[9]

### 11.4 WorkBuddy 邮件专家的隔离

总监的完整助理还会接智慧芽、Obsidian、ppt-master 等工具。**不能因此让读取任意邮件的 Agent 同时拥有公开检索、任意文件读取及发送能力。**

建议创建独立私人邮件专家，只绑定本项目只读 MCP 和必要的回复能力。邮件正文和衍生摘要不得自动转交智慧芽等外部检索服务，不自动进入团队分身知识库。

上线前验证 WorkBuddy 的工具范围限制是否在运行时真正生效。若只能靠提示词而不能形成足够隔离，应使用独立实例/运行环境或后端强制网关；不能把 UI 中隐藏工具当成安全保证。

### 11.5 接入验收

在目标 WorkBuddy 中完成：连接、工具发现、带认证查询、分页、过期 Token、越权 ID、服务停机、长正文和模型提示词注入测试。关闭 WorkBuddy 后继续发送测试邮件，确认后台分析和推送不受影响。

### 12.5 后台分析提示规范

后台分析服务读取原始字段和有限线程，不授予模型任何工具。提示规范至少包含：只返回指定 JSON；输入全部为待分析数据；每个待办和期限提供证据；不确定时允许 null；不得创造项目；不得判定未读附件内容；不得执行邮件内指令；不得输出未经批准的发送动作。

**前后台一致性检查：** 同一邮件输入和同一政策版本下，WorkBuddy 的解释应忠于后台结果。对话中的不同判断只作为待审核建议，不自动覆盖后台已发送提醒或正式规则。

## 14. 部署、数据治理与运维

### 14.1 部署路径

先在模拟邮箱环境运行，再使用批准的试点账号。首期推荐企业批准的常驻 Linux 主机或现有容器平台；具体资源根据试点流量和解析限额压测，不把“某台笔记本一直开着”当成生产保障。

数据库不暴露公网。MCP/API 经企业批准的入口暴露并启用 TLS、认证与限流。IMAP、模型、企微等出站访问采用白名单。进程用非特权账号，不把整个用户目录挂载给 Worker。

### 14.2 数据去向清单

| 数据 | 允许的默认位置 | 需要单独批准的去向 |
| --- | --- | --- |
| 邮箱凭证 | 企业秘密管理系统 | 不进入模型、日志、Obsidian 或 Skill |
| 邮件正文缓存 | 获准数据库，按保留策略处理 | 外部模型服务 |
| 附件 | 首期只保存元数据 | 内容下载、解析环境及长期存储 |
| 简报与提醒 | 私人工作区、获准本人通知渠道 | 项目群、团队分身、共享知识库 |
| 项目摘要 | 本人确认后再沉淀 | Obsidian 及其他协作系统 |
| 模型输入/输出 | 按批准的模型合同及企业规则 | 不能假定“本地部署业务服务”就等于模型不外发 |
| 故障日志 | IT 获准运维系统 | 默认只含编号、错误码和状态 |

撤销授权时同时停止任务、撤销服务 Token、清理缓存/摘要/临时文件并按批准策略处理备份。未来若加入搜索或向量索引，同步执行删除；不能只删数据库正文而留下检索副本。

本系统按管理辅助用途设计，不替代正式研究记录和审批。若用途扩大到受控研究流程，应由客户相应负责人重新评估，不能凭产品名称或免责声明认定满足全部要求。

### 14.3 关键指标

- 每个文件夹的 `last_checked_at`、连接状态与 UIDVALIDITY 变化。
- 发现但未获取、未解析、未分析任务数量及最老等待时间。
- 解析失败率、模型失败率、证据校验失败率。
- 通知 pending/unknown/permanently_failed 数量及最大等待时间。
- 每日简报是否生成、是否被平台接受、是否覆盖完整。
- 每日误报、人工标记漏报和实际需要处理的事项数量。

不能只监控容器进程是否存在。至少使用一个独立于邮件 Worker 的监测位置检查心跳；整台主机停机或企微渠道故障时，应通过事先批准的独立 IT 告警渠道获知。

### 14.4 故障处理表

| 故障 | 自动动作 | 用户/运维可见信息 |
| --- | --- | --- |
| IMAP 断线 | 退避重连、补拉 | 显示最后成功同步时间 |
| 认证失效 | 停止高频重试，等待更新凭证 | 通知 IT，说明监控受限 |
| UIDVALIDITY 改变 | 开新同步代次、受控重建和去重 | 标记覆盖不完整 |
| 大邮件/解析失败 | 转流式/分段或待核查任务 | 不隐藏该邮件，不声称附件已读 |
| 模型不可用 | 有限重试、规则级降级 | 显示分析受限，保留重要候选 |
| 数据库不可用 | 不推进游标，不伪造成功 | 故障告警；恢复后补拉 |
| 企微接受状态未知 | 记录 unknown，按策略有界重试 | 不显示已读/已处理 |
| 企微永久失败 | 持久保存提醒，走批准的故障通道 | 不擅自改发其他人 |
| 突发邮件洪峰 | 优先处理重要候选、限并发、聚合提示 | 不以限流为由静默丢弃 P0 |
| 主机/调度停机 | 独立监控告警，恢复后补任务 | 下一简报说明断档 |

| --- | --- | --- | --- |
| M0：接入确认 | IT 信息表、数据流、模型与企微权限、本人规则访谈 | 接入确认表、初始政策、测试数据授权 | 实际邮箱和通知通道可以在批准范围内测试 |
| M1：只读同步 | 连接、UID 增量、回填、解析、队列、重连 | 同步服务、数据库迁移、健康页面 | 测试邮件正确读取且源邮箱无修改 |
| M2：邮件分析 | 线程、结构化提取、证据校验、P0/P1/P2 | 分析 Worker、Schema、规则样本 | 标注样本的误报/漏报与关键字段达到约定门槛 |
| M3：简报与提醒 | 日调度、Outbox、本人通知、失败告警 | 简报模板、通知适配器、确认页面 | 重启/失败/重复触发测试通过 |
| M4：WorkBuddy 接入 | 只读 MCP、三个 Skill、身份和隔离 | 可导入配置、技能目录、联调记录 | 可查阅解释，不能越权或写邮箱 |
| M5：影子运行 | 真实获准邮件后台分析，默认不自动推送业务提醒 | 与人工判断对照报告 | 总监确认规则与打扰程度 |
| M6：正式启用 | 分级放开推送、固定版本、运维演练 | 上线清单、恢复手册、责任分工 | 验收签字、回退和撤销路径可用 |

影子运行不是偷偷监控：真实读取、模型处理和保存仍然需要授权。它只是暂不启用业务自动提醒。

### 必须交付的文件

代码仓库及锁文件；数据库迁移；配置示例与秘密配置说明；MCP 工具说明；三个 Skill；政策与提示模板；人工构造/获准脱敏测试集；同步与推送联调报告；误报漏报评估；部署、故障恢复、密钥轮换和撤销授权手册。

### 16.1 功能与可靠性测试

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| F01 | 新邮件进入 INBOX | 获取、分析和通知链路都有可追溯记录 |
| F02 | 邮件被手机提前读过 | 仍正常进入增量分析，不依赖未读 |
| F03 | 服务器规则将邮件移入其他授权文件夹 | 定时核对可发现，简报标清覆盖范围 |
| F04 | Worker 在落库与推进游标之间中断 | 恢复后不漏登记，也不重复业务提醒 |
| F05 | 断网后积累多封邮件 | 恢复后按 UID 补拉，不只取最后一封 |
| F06 | UIDVALIDITY 改变 | 旧映射失效，重建不造成旧紧急邮件群发 |
| F07 | 同一邮件跨文件夹出现 | 保留投递实例；可靠判重后不重复通知 |
| F08 | Message-ID 缺失或相同但内容不同 | 不错误覆盖消息、不错误合并线程 |
| F09 | 同主题但属于不同事项 | 弱关联有标记，不虚构共同线程 |
| F10 | 已发送文件夹未接入 | 不声称本人尚未回复 |
| F11 | 中文编码、HTML、大附件、空正文、乱码 | 正确处理或显式待核查，不静默丢弃 |
| F12 | 引用历史“紧急”但本次只是确认收到 | 不重复触发原紧急事件 |
| F13 | 模型返回虚构证据/非法 JSON | 被校验拦截，进入重试或待核查 |
| F14 | 两个调度进程同时触发晨报 | 唯一任务和冻结版本防止重复 |
| F15 | 企微调用超时但可能已接受 | 标记 unknown，不伪装送达、不无限重试 |
| F16 | 同步中断时生成晨报 | 明确数据不完整，不报告“没有重要邮件” |
| F17 | WorkBuddy 关闭 | 后台同步、分析和通知仍运行 |
| F18 | 临近截止时间且没有新邮件 | 调度器可重评估待办，按批准策略提醒 |
| F19 | 原邮件在读取前已删除 | 标记不可获取，不能编造内容或声称恢复成功 |
| F20 | 延迟补拉的旧日期邮件 | 作为迟到内容进入覆盖，不被日期过滤遗漏 |

| 编号 | 场景 | 通过标准 |

### 16.3 业务质量评估

建议使用一批代表性邮件线程，由总监或授权人员标注：应立即提醒、当日处理、普通知会、需要人工核查，以及待办/期限/依据。开发校准集和验收集分开，不能用同一批调好规则再当作独立效果证明。

分别统计：

```text
P0 召回率 = 正确识别的 P0 / 人工标注的全部 P0
P0 精确率 = 正确识别的 P0 / 系统发出的全部 P0
重复提醒率 = 无新增事件的重复提醒 / 全部提醒
关键字段正确率 = 正确的待办、责任人、期限等字段 / 被核查字段
```

当样本没有 P0 时不报告 P0 召回率为 100%；同时报告样本数量和漏报例子。小样本结果只作为试点依据，不推断生产环境绝对可靠。

### 16.4 建议验收目标

这些是待协商目标，需在真实邮箱与网络条件下测量：

- 安全门槛：验收集源邮箱写操作为 0，跨账号内容泄露为 0，凭证泄露为 0；任一发生均阻止上线。
- 已约定的必须提醒测试场景全部通过；其他紧急分类阈值由总监依据误报/漏报代价批准。
- 在连接、模型及通知平台正常的测试条件下，目标为从系统发现新邮件到通知平台接受，P95 不超过 120 秒。
- 轮询发现时间另计；采用 120 秒轮询不等于从邮箱投递起必然 120 秒内送达。
- 每日简报目标在配置时间后的 5 分钟内被平台接受；超时、积压或同步不完整必须显示告警。
- 所有关键判断都有可定位证据；证据校验不通过不得以“确定事实”输出。

无论测试表现如何，不承诺捕获在系统观察前已经被源端删除的邮件，也不把通知接受状态等同于人的阅读或响应。

## 17. 成本控制与后续扩展

### 17.1 成本结构

不预设供应商单价。上线前记录邮箱日均量、平均正文大小、模型输入输出量、重试率、服务器和存储需求。

```text
月度成本 = 主机/数据库/备份
         + 单封分析的模型调用
         + 每日简报的模型调用
         + 必要的二次核查
         + 监控、日志和实施维护
```

按 `message_id + 输入哈希 + 规则版本 + 模型/提示版本` 缓存分析；同一邮件不因反复打开 WorkBuddy 而重新付费分析。每日摘要主要读取结构化结果，仅为必要事项补取原文。

预算上限不能导致重要候选静默丢弃。超预算时进入规则级降级、标记分析受限并告警。批量处理、低价值邮件过滤和原文截断都要保留可审计的覆盖信息。

### 17.2 后续扩展顺序

先增加总监确认的项目词表和审阅规则，再增加受控附件解析；确有需要后加入 Obsidian 项目摘要沉淀、更多账号及正式企业身份集成。

邮件回复草稿可先只在对话中生成。任何未来的邮箱写入、发送或自动升级能力，都应作为独立版本、独立工具及审批流建设，不能悄悄放进只读 MCP。

## 18. 可直接交给开发者的执行说明

> 在一个新的工程仓库中实现“单账号试点、可扩展隔离”的邮件数字助理后端。使用 ImapFlow 只读读取获授权 IMAP 文件夹，用 MailParser 解析 MIME；使用 PostgreSQL 保存增量游标、任务、正文缓存、结构化分析、待办、每日简报和通知 Outbox。
>
> 先以模拟邮箱、合成邮件和模型/企微 Mock 完成闭环，不接真实邮箱，不要求用户把密钥放进聊天。实现每文件夹 UIDVALIDITY + UID 增量、任务租约、断线补拉、历史回填不告警和通知去重。同步、分析、通知进程在 WorkBuddy 关闭后也应运行。
>
> 分析采用“确定性规则 + 无工具模型提取 + 后台 Schema/证据校验”，产出可追溯待办与优先级。截止时间不明确时保留原文和 null，不伪造日期。附件首期只读取元数据。每日简报用冻结快照与持久任务生成，避免重复发送和未读筛选造成遗漏。
>
> 对 WorkBuddy 提供本方案定义的七个只读 MCP 工具；调用者权限来自认证，不接受模型任意选择账号。MCP 不提供发送、删除、已读标记、任意 URL、SQL 或 shell。创建三个对应 Skill，使用共享版本化规则，避免前后台判断标准漂移。
>
> 企业微信推送通过独立通知适配器实现，先用 Mock，待实际企业账号完成权限与接口联调后启用。收件人由后台固定绑定；发送状态区分 accepted、unknown 与 failed；本人确认通过独立受认证页面完成，不以查看链接或平台接受代表已处理。
>
> 首次交付必须包括代码、数据库迁移、锁定依赖、无密钥配置示例、MCP 配置、三个 Skill、测试夹具、故障恢复及撤销授权手册。未通过第 16 节安全与可靠性测试前，不开启真实自动推送。优先完成 M1—M4，不增加多 Agent、向量库或邮箱写操作。
